# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A Databricks AI Runtime (AIR) demo for DAIS: fine-tune `Qwen/Qwen3.5-4B` with Hugging Face TRL supervised fine-tuning + PEFT LoRA on IBM TabFormer credit-card fraud transactions, register the merged model to Unity Catalog as a custom LLM, deploy it to Mosaic AI Model Serving (vLLM), and load test the endpoint at high QPS. The deliverables are Databricks notebooks plus YAML configs — there is no test suite, linter, or build step.

## Commands

```bash
# Local environment (only needed for Databricks Connect execution — the torch/HF
# block in requirements.txt is GPU-compute only and can be skipped locally)
python -m venv .venv && source .venv/bin/activate
pip install -r train/requirements.txt

# Verify CLI auth (profile DEFAULT; workspace host is in databricks.yml)
databricks auth profiles

# Run the ingestion notebook locally via Databricks Connect (serverless)
.venv/bin/python setup/01_load_tabformer_dataset.py

# Submit training via the AI Runtime CLI (alternative to the notebook's @distributed cell).
# COPYFILE_DISABLE=1 is required on macOS: without it bsdtar synthesizes AppleDouble
# (._*) entries in the code snapshot tarball from file xattrs; the remote launcher
# resolves $CODE_SOURCE_PATH from the tarball's first entry and picks `._train`,
# failing with "can't open file '/databricks/code_source/._train/train.py'".
# The CLI's own --exclude='._*' can't catch these (they're synthesized at archive
# time, not read from disk), and bsdtar hides them from `tar -tzf` listings —
# inspect snapshots with Python tarfile.getnames() instead.
cd train && COPYFILE_DISABLE=1 air run --file train.yaml --watch

# Bundle operations (Declarative Automation Bundle, target: dev)
databricks bundle validate
```

The training runner notebook (`train/runner.py`) **cannot run locally** — it requires Databricks Serverless GPU with the AI Runtime `AI v6` environment (`serverless_gpu.distributed`, H100/A10 GPUs). Run it as a workspace notebook. The load-test notebook runs on Databricks serverless compute.

## Databricks Notebook Source Format

Every `.py` file in `setup/`, `train/`, and `load_test/` is a Databricks notebook **except `train/train.py`**, which is a plain Python module holding the training implementation (imported by the training notebook and executed directly by the AI Runtime CLI per `train/train.yaml`). When editing notebooks, preserve the format: `# Databricks notebook source` header, `# COMMAND ----------` cell separators, `# MAGIC %md` markdown cells.

- Every consumer (the three notebooks, `train.py`, local scripts) gets the shared helpers (`load_yaml_config`, `config_str`/`config_int`/`config_float`/`config_bool`, `quote_identifier`, `full_name`, `get_spark_session`, `load_training_config`, `init_training_workspace`) the same way: insert the `train/` directory into `sys.path`, then `from training_utils import ...`. Never `%run` it, and never add the `# Databricks notebook source` header to it — notebook-formatted files cannot be imported in the workspace (`NotebookImportException: Importing notebooks directly is not supported`), and `train.py` must be able to import the module under the runner notebook, the AIR CLI, and local runs alike.
- The helpers module must **never** be renamed back to `utils.py`: the Databricks AI GPU base environment's `nvidia_cutlass_dsl` package registers a top-level `utils` module once torch/CUDA loads (e.g. when `train.py` imports `trl`, which pulls in transformers and torch), poisoning `sys.modules` so a local `from utils import ...` resolves to cutlass's vendored module and fails with `ImportError: cannot import name ... from 'utils' (...nvidia_cutlass_dsl/...)`.
- Training config flows through `training_utils.load_training_config()`, which returns a flat dict that the runner notebook and `train.py` each bind with `globals().update(...)` — so both see identical constants (`MODEL_NAME`, `TRAINING_OUTPUT_DIR`, `sft_table_q`, ...). It reads `parameters.training_config` from the YAML file at `$HYPERPARAMETERS_PATH` when AIR sets it (so `air run --override` values reach the script), falling back to `train.yaml` next to `training_utils.py`. It is deliberately a function, not top-level module code, so importing `training_utils` has no side effects (no config parse, no Spark, no schema creation). `load_yaml_config` resolves paths against the module's own directory by default; callers in other folders (the load-test notebook) pass `base_dir=Path.cwd()` for their own YAML.
- Notebooks support dual execution: inside Databricks (serverless notebooks, where `Path.cwd()` is the notebook's folder) or locally via Databricks Connect. `get_spark_session()` in `training_utils.py` attaches a serverless Connect session when none exists; `setup/01_load_tabformer_dataset.py` resolves its own directory via `__file__` with a `dbutils` notebook-context fallback before importing the helpers from `train/`.

## Architecture: Three-Stage Pipeline Coupled by YAML Configs

Each stage is a notebook driven by a sibling YAML file, connected to the next stage only through Unity Catalog objects:

1. **Ingest** — `setup/01_load_tabformer_dataset.py` + `setup/setup.yaml`: downloads TabFormer into a UC staging volume, writes the cleaned transaction table (`fraud_dataset`) and the SFT table (`fraud_sft_dataset`) with `prompt`, `assistant_response`, and `shard_id` columns, then exports the SFT records to the `training_data` volume as Parquet partitioned by `shard_id` (the AIR data-loading pattern for large Delta tables). **Overwrites the tables and the export on every run.** Creates the schema and volumes if missing.
   `setup/02_load_model_weights_to_volume.py` (same `setup.yaml`) is an optional adjunct to this stage: it mirrors the `model_name` checkpoint from the Hugging Face Hub into the `model_volume` volume, one file at a time (download to local disk → stream to the volume → delete the local copy), so local disk stays bounded and volume writes stay sequential (parallel large safetensors writes to volume FUSE hit EAGAIN). It resolves `model_revision` to a commit SHA and fetches every file at that SHA, skips files already present at the Hub-reported size unless `force_model_download`, writes provenance to `<model>_download_metadata.json` **beside** (not inside) the weights directory so the mirror stays a byte-for-byte Hub snapshot, and verifies config/tokenizer/index-shard completeness. Nothing consumes it automatically — point training at it by setting `train.yaml`'s `model_name` to the `/Volumes/...` path.
2. **Train / register / deploy** — `train/runner.py` + `train/train.yaml` (one file: top-level AIR CLI workload schema with the demo's own configuration nested under `parameters.training_config`, the schema's designated field for custom structured config — the AIR CLI rejects unknown top-level keys): reads the SFT table, fine-tunes with TRL `SFTTrainer` + PEFT LoRA, saves rank-0 adapters to a UC volume, then (in later cells) merges the adapter, registers to UC, and creates/updates the serving endpoint. The training implementation is `train/train.py` (`run_rank_training()` trains one rank's shard slice; rank/world size are resolved launcher-agnostically); the notebook's `@distributed(gpus=N, gpu_type="h100")` cell is a thin wrapper that inserts `NOTEBOOK_DIR` into `sys.path` on each worker and calls it, and the AI Runtime CLI runs the same file standalone (`air run --file train.yaml`). The registration cell imports `load_adapter_model` from the same module (`AutoPeftModelForCausalLM` + tokenizer, which it then `merge_and_unload()`s). Creates the schema and the checkpoint volume if they don't exist (the SFT table itself still comes from setup).
3. **Load test** — `load_test/load_test_serving_endpoint.py` + `load_test/serving_load_test.yaml`: samples prompts from the SFT table, smoke-tests the endpoint, then generates paced async HTTP traffic from Spark tasks via `mapInPandas` + `aiohttp`. **Appends** a summary row to the results Delta table.

### Cross-file contracts (keep these in sync)

- **Config coupling**: `catalog`, `schema`, and `sft_table` must agree across all three YAML files (the training values sit under `train.yaml`'s `parameters.training_config` key); `endpoint_name` must match between `train.yaml` and `serving_load_test.yaml`; `setup.yaml`'s `table` must equal `train.yaml`'s `source_table`; `setup.yaml`'s `model_name` must equal `train.yaml`'s `model_name` unless `train.yaml` has been repointed at the mirrored `/Volumes/...` path (the mirror is only useful if it holds the checkpoint training loads); `sft_volume` must match between `setup.yaml` and `train.yaml` (it locates the Parquet export training reads). `train.yaml`'s top-level `experiment_name` is the only place the MLflow experiment is named — it must stay alphanumeric/`-`/`_` (it becomes a Jobs API task key) because AIR resolves it to `/Users/<user>/<experiment_name>`, and the runner notebook resolves the same name to the same path via `training_utils.resolve_experiment_path()`.
- **Shard contract**: ingestion computes `shard_id` as `pmod(xxhash64(...), sft_shards)` (128 shards) and exports the SFT records as Parquet partitioned by `shard_id` into `/Volumes/<catalog>/<schema>/<sft_volume>/<sft_table>/shard_id=N/`. `run_rank_training()` claims the directories where `N % world_size == rank` and loads them with Hugging Face `datasets` (`load_dataset("parquet", ...)`) — no Spark session on the GPU workers. Sampling is two-level: for `sample_fraction < 1` only a seeded-random subset of the rank's shard directories is loaded (hash shards are uniform, so this is equivalent to row sampling) and row-level sampling within the loaded shards lands on the exact fraction — this keeps the HF `datasets` Arrow conversion ("Generating train split") proportional to the fraction instead of always materializing the full slice, per https://docs.databricks.com/aws/en/machine-learning/ai-runtime/dataloading#load-large-delta-tables-using-volumes. Parquet was chosen because training consumes HF `datasets`, which memory-maps Parquet natively.
- **Prompt contract**: the prompt text is built once in ingestion (Spark `concat` expressions) and the assistant response is compact JSON with keys `risk`/`action`/`reason`. Training, the sample serving payload, and the load test all reuse this exact shape; if you change the prompt template in setup, the sample payload in the training notebook must match. The contract also includes **thinking suppression**: `train.py` renders with `CHAT_TEMPLATE_KWARGS = {"enable_thinking": False}` and every request must send `chat_template_kwargs={"enable_thinking": false}` (the notebook's sample payload hardcodes it; the load test reads `enable_thinking` from `serving_load_test.yaml`). If the two ever disagree, the fine-tune's direct-JSON behaviour stops matching the serving render.
- **Serving contract**: registration wraps merged HF weights in an MLflow pyfunc whose `metadata` carries `task: llm/v1/chat` and a vLLM OpenAI-server `entrypoint` listening on port 8080 (the port Model Serving expects), with `--language-model-only` so only Qwen3.5's text backbone is served. The entrypoint launches from the model's `artifacts/` folder, so the `--model` path must be the bare artifact name — an `artifacts/` prefix makes vLLM treat it as a Hugging Face repo id and fail with a 401. Entrypoint models must be registered with `env_pack="databricks_model_serving"` (express deployment), which needs `databricks-sdk>=0.102.0` to avoid a 5-minute timeout uploading the env-pack tarball. The pyfunc placeholder class is deliberately defined inline in the registration cell so cloudpickle serializes it by value — no `code_paths` are logged, and none are needed as long as the logged model imports nothing from the repo (the vLLM entrypoint, not the pyfunc, serves traffic). The serving container's environment is **not** declared in `pip_requirements`: it is installed in the notebook in two `pip` passes (`vllm==0.24.0` + `transformers==5.13.0` + `mlflow==3.14.0` + `flashinfer-cubin`, then `opencv-python-headless==4.12.0.88` on top) and captured by `env_pack`. `log_model` passes only `extra_pip_requirements=["mlflow==3.14.0"]`. A single requirements list is resolved in one pass and cannot hold both vLLM's `opencv>=4.13` floor and the FIPS-safe 4.12 pin — see the opencv/FIPS bullet below. Both sides now run transformers 5, so the old training-5/serving-4 straddle is gone. vLLM settings (`vllm_dtype`, `vllm_max_model_len`, `vllm_gpu_memory_utilization`) come from `train.yaml`'s `parameters.training_config`.

### Ordering dependencies inside the training notebook

Registration is now **three cells**, because the training and serving environments cannot share one Python session:

1. **Merge** — needs `TRAINED_ADAPTER_OUTPUT_DIR`/`TRAINING_RUN_ID` from the training cell. Loads the rank-0 adapter, `merge_and_unload()`s it, and writes plain HF weights to `/local_disk0/air-demo-merged/<artifact>` (local disk, not `/Volumes`: it survives the restart below and avoids the EAGAIN failures large safetensors writes hit on the volume FUSE mount). It then writes `merge_metadata.json` next to them.
2. **Install the serving stack** — two `pip` passes (vLLM first, `opencv-python-headless==4.12.0.88` second) followed by `%restart_python`.
3. **Register** — the restart wipes all session state, so this cell re-inserts `sys.path`, re-runs `load_training_config()`, re-sets the MLflow experiment, and reads `merge_metadata.json` for the adapter dir, training run id, and merged-weights path. **State crosses the restart boundary through that file, never through Python globals** — if you add anything the registration cell needs, put it in the JSON.

The deployment cell requires `REGISTERED_MODEL_VERSION` from registration (`register_model`/`deploy_endpoint` flags in `train.yaml`'s `parameters.training_config` gate these). Registration is deliberately separate from training so a failed registration or deployment can be rerun without re-training. Scaling is done by editing only the `gpus=` value in the `@distributed` decorator on the single training cell. The dataset sampling fraction is config-driven for both launchers: `load_training_config()` binds `train.yaml`'s `training_sample_fraction` as `TRAINING_SAMPLE_FRACTION`, and the training cell forwards it into `run_rank_training(sample_fraction=...)` — change the YAML (or `air run --override parameters.training_config.training_sample_fraction=...`) rather than reintroducing a hardcoded value in the cell.

### Other constraints

- The training environment is **serverless GPU environment version 6** (Public Preview; `environment.version: '6'` in `train.yaml`, `AI v6` in the notebook compute picker): Python 3.12, CUDA 13, transformers 5.8, trl 0.24, peft 0.19, accelerate 1.13, datasets 4.8, flash-attn 2.8/3.0. v6 **removed `bitsandbytes`, `xformers`, and `unsloth`** from the base image and no longer bundles torch in any base environment — hence the explicit `torch==2.11.0` pin in `train.yaml`/`requirements.txt` (it must match v6's CUDA 13 build) and `optim="adamw_torch_fused"` instead of the old `adamw_8bit` (which needed bitsandbytes; with LoRA the optimizer state is negligible either way). Declarative bundles select the same image with `base_environment: databricks_ai_v6`. The AIR CLI workload schema value for v6 is not in the published docs — `'6'` mirrors the v5 spelling and is the thing to check first if a submission is rejected.
- **opencv/FIPS is a resolution-time constraint, not a wall** (re-verified 2026-09-21). `opencv-python-headless>=4.13` still aborts vLLM at startup with `FATAL FIPS SELFTEST FAILURE` on Model Serving's FIPS pods, and the upstream bug (opencv/opencv-python#1191) is still open — so opencv must stay at `4.12.0.88`. But vLLM only needs opencv for video IO, so the standard internal workaround is to install a **modern vLLM first, then force `opencv-python-headless==4.12.0.88` in a SECOND pip pass** and accept pip's conflict warning. Field-validated on Custom LLM Serving in July 2026 (Gemma 4 12B on `GPU_MEDIUM`) with `vllm==0.24.0` + `transformers==5.13.0` + `mlflow==3.14.0` — note `mlflow==3.12` is uninstallable next to vllm 0.24 (starlette conflict). A single `pip_requirements` list is resolved in one pass, so the conflicting pins **cannot** be expressed there; the working pattern installs both passes in the notebook and lets `env_pack` capture that environment (Databricks' own starter notebook passes only `extra_pip_requirements=["mlflow==3.12.0"]` and lets MLflow infer the rest). Trade-off to state to customers: opencv `<4.13` carries a known RCE CVE, which is why the managed Foundation Model path still treats this as blocked while per-model pins work.
- Qwen3.5 serving is what this repo now does, on the two-pass path above (internally it has also run on vLLM 0.17.0 for notebook evals and 0.18.0 for `Qwen/Qwen3.5-122B-A10B-FP8`). `--reasoning-parser qwen3` is the alternative if thinking ever has to stay on: it splits reasoning into `reasoning_content` so `content` stays clean JSON, at the cost of a much larger `max_tokens` budget.
- Databricks' current custom-LLM starter notebook (docs page updated 2026-09-11) pins `vllm==0.11.2`, `transformers==4.57.6`, `opencv-python-headless==4.12.*`, `mlflow==3.12.0`, `databricks-sdk>=0.102.0`, and **`flashinfer-cubin==0.5.2`** — those precompiled cubins are a cleaner fix for the missing `ninja`/`nvcc` than this repo's `VLLM_USE_FLASHINFER_SAMPLER=0`. Never pin `flashinfer-cubin` yourself: vLLM requires an exact version (0.11.2→0.5.2, 0.24.0→0.6.12), so a mismatched pin fails with `ResolutionImpossible`; let vLLM pull it. and `env_pack` is required because custom LLM serving runs on [Serverless Optimized Deployments](https://docs.databricks.com/aws/en/machine-learning/model-serving/serverless-optimized-deployments). Supported workload types are `GPU_SMALL` (T4), `GPU_MEDIUM` (A10), `GPU_XLARGE` (H100).
- **Qwen3.5 has no non-thinking variant** — thinking is on by default, and an unsuppressed reasoning preamble truncates the JSON at `max_tokens`. Suppression must hold on both sides (see the prompt contract). This is also why `train.py` applies the chat template itself instead of letting TRL do it: that is the only way `enable_thinking=False` reaches the render. `Qwen3.5-4B` is natively multimodal (`Qwen3_5ForConditionalGeneration` + `vision_config`), but training loads the text backbone through `AutoModelForCausalLM` → `Qwen3_5ForCausalLM` (the documented text-only path) and serving passes `--language-model-only`.
- Qwen3.5's attention stack is **3:1 hybrid** — three Gated DeltaNet (linear attention) layers per Gated Attention layer, per the checkpoint's `layer_types`. LoRA therefore lands on `q/k/v/o_proj` only in the full-attention layers plus every layer's MLP projections; the DeltaNet `linear_attn.*` projections are deliberately unadapted. The DeltaNet path also wants the optional `causal_conv1d` and `fla` packages for its fast kernels — without them transformers silently falls back to slower, more memory-hungry PyTorch ops, so add them if training throughput matters (neither is installed here, to keep the env build simple).
- Custom LLM serving beta does not support scale-to-zero with `GPU_XLARGE` — the deploy cell raises if both are set.
- Capacity is **fixed** during beta (no autoscaling between replicas): `serving_workload_size` sets the replica count and requests beyond provisioned capacity are rejected with instant 429s (the threshold is not user-configurable). Measured on this workload: one `GPU_MEDIUM` (A10) replica sustains ~150 successful QPS at ~1.1-1.4s latency with `max_tokens: 64-128`. Size for peak: 10K QPS needs `Large` + `GPU_XLARGE`-class capacity or multiple endpoints sharded client-side. The load generator itself caps out at (cluster task slots) × (per-worker rate) — `load_generator_workers` must not exceed available Spark task slots or achieved QPS silently falls short with zero 429s.
- The serving container has no `ninja`/`nvcc`, so FlashInfer (present in the Databricks AI base env) cannot JIT-compile kernels — vLLM crashes at sampler warmup with `FileNotFoundError: 'ninja'` unless the served entity sets `VLLM_USE_FLASHINFER_SAMPLER=0` (done via `environment_vars` in the deploy cell; this is runtime config, no re-registration needed).
- **Training stack contract** (`train/train.py`): assistant-only loss comes from TRL's prompt-completion dataset format — each row is mapped to a conversational `prompt` (user turn) plus `completion` (assistant turn) and `completion_only_loss=True` masks the prompt, replacing hand-written response markers. `SFTConfig` takes `max_length` (TRL renamed `max_seq_length` in 0.20), and `LoraConfig` is passed to `SFTTrainer` as `peft_config` rather than pre-wrapping the model: TRL applies the adapter and calls `enable_input_require_grads()` so gradient checkpointing yields adapter gradients, and it rejects an already-PEFT-wrapped model when `peft_config` is set. `optim="adamw_8bit"` is why `bitsandbytes` stays in the dependency list.
- Multi-GPU DDP needs **non-reentrant** gradient checkpointing (`gradient_checkpointing_kwargs={"use_reentrant": False}` in `SFTConfig`): the reentrant implementation fires each LoRA parameter's gradient hook twice and dies with "Expected to mark a variable ready only once". `ddp_find_unused_parameters=False` is set explicitly — every LoRA parameter gets a gradient each step, and the unused-parameter scan conflicts with checkpointing.
- Both launchers log to the experiment named by `train.yaml`'s top-level `experiment_name`; nothing is hardcoded per user, and no path should be re-added to the notebook. `resolve_experiment_path()` prefixes the current user (via `WorkspaceClient().current_user`, so it needs no Spark session) and passes through a value that already starts with `/`. The runner notebook calls it once (`MLFLOW_EXPERIMENT_PATH`), sets it on the driver, and forwards it into `run_rank_training(experiment_path=...)` so the rank-0 GPU worker logs there instead of relying on the launcher to propagate the driver's active experiment. AIR CLI runs pass `None` — AIR already created the workload run in that experiment — and a bare `python train.py` resolves the name itself in `main()`.
- Only `README.md`, `CLAUDE.md`, `databricks.yml`, `setup/`, `train/`, and `load_test/` are version-controlled; `demo_script/`, `.claude/`, `.github/`, `.vscode/`, and other agent/IDE artifacts are gitignored.
